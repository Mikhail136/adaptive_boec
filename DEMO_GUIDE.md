# DEMO GUIDE: Адаптив-Боец

## Назначение демонстрации

Показать, что при ограниченной пропускной способности канала связи обычная
передача по порядку уступает адаптивной обработке потока.

Демонстрация сравнивает два режима:

1. **Baseline** — пакеты идут в канал в исходном порядке.
2. **Adaptive** — поток проходит через дедупликацию, агрегацию телеметрии и
   приоритетный планировщик.

## Короткий сценарий показа на 3–5 минут

### 1. Объяснить проблему

Современный оператор получает смешанный поток: координаты, телеметрию, команды,
сенсорные данные, видео и сервисные сообщения. Когда канал перегружен,
второстепенные данные могут вытеснить критически важные.

### 2. Показать структуру проекта

```text
adapters/     генераторы и упаковщики входных данных
channel/      модель ограниченного канала связи
core/         логика оценки, сжатия, дедупликации, планирования и метрик
experiments/  демонстрационные сценарии
tests/        автотесты MVP
```

### 3. Запустить тесты

```bash
python -m pytest
```

Ожидаемо: все тесты должны пройти.

### 4. Запустить перегруженный сценарий

```bash
python experiments/run_demo.py --scenario overload
```

Что показать в выводе:

- сколько пакетов доставлено;
- сколько критических сообщений доставлено;
- сколько данных реально заняло канал;
- сколько пакетов отброшено из-за нехватки полосы.

### 5. Запустить аварийный сценарий

```bash
python experiments/run_demo.py --scenario emergency
```

Смысл: даже при сильном ограничении канала адаптивный режим должен лучше
сохранять важные сообщения.

### 6. Экспортировать отчёт

```bash
python experiments/run_demo.py --scenario emergency --export-dir reports
```

После запуска появятся файлы:

```text
reports/emergency_report.json
reports/emergency_report.csv
```

Их можно приложить к конкурсным материалам или использовать для графиков.

## Что говорить жюри

Ключевая формулировка:

> Проект не пытается заменить систему связи. Он демонстрирует управляющий слой,
> который перед отправкой анализирует поток, снижает информационный шум и
> отдаёт ограниченный канал наиболее важным сообщениям.

## Сильные стороны проекта

- понятная инженерная постановка задачи;
- модульная архитектура;
- воспроизводимые эксперименты через `seed`;
- сравнение baseline/adaptive;
- метрики эффективности;
- автотесты;
- возможность расширения до интерфейса и графиков.

## Ограничения, которые нужно честно назвать

- это демонстрационная модель, а не реальная система связи;
- нет криптографии и интеграции с радиопротоколами;
- видеопоток имитируется строковыми данными;
- модель канала упрощённая;
- правила приоритета экспертные, а не обученные на реальных данных.

## Возможные вопросы и ответы

### Почему это называется адаптивной системой?

Потому что обработка зависит от состояния канала и типа данных: при ограниченной
полосе система сохраняет критические пакеты, снижает повторы и уменьшает поток
частой телеметрии.

### Почему не используется нейросеть?

Для MVP выбрана объяснимая экспертная логика. Это безопаснее для демонстрации:
можно показать, почему конкретный пакет получил высокий приоритет. В будущем
можно добавить ML-модель как отдельный модуль оценки важности.

### Что можно улучшить дальше?

- добавить графический интерфейс;
- добавить реальные графики метрик;
- добавить несколько профилей канала;
- добавить обучение весов приоритета;
- добавить имитацию очередей, задержек и подтверждений доставки;
- добавить экспорт презентационного отчёта.
